# DEFENSE: Medical-ChatBot (Mr. Healthcare)

**What it does.** It answers basic questions about diseases and symptoms (symptoms, causes, prevention, treatments, complications, descriptions) from a knowledge graph of 658 diseases. When the graph has no answer, it says so instead of guessing. It keeps a conversation going without a language model: follow-ups such as "what causes it?" reuse the confirmed topic, ambiguous names and likely misspellings are confirmed with the user, refusals say why, and suggested next questions are only ones the graph can answer. It also understands a few sourced other names, such as "whooping cough" for pertussis. A language model may read the question first to catch phrasings and negations the keywords miss, but it only picks among names the rules found; every answer is still a graph fact. Long answers show their own headings and numbered points, and a more conversational wording appears only for fields the owner has approved against the original.

**How it works.** The page sends the question to a Flask API. The API finds known disease and symptom names in the question with an Aho-Corasick automaton, works out the intent from whole-word keywords, runs a fixed parameterized Cypher query against Neo4j, and turns the rows into a structured reply. When the model is on, it is asked after every local check (aliases, typos, type ambiguity, unsupported questions) and returns only candidate ids and question types, validated locally; any failure falls back to the rules within 2 s. Words inside a matched name are hidden from keyword matching, so a name such as "deep palm infection" is not read as a question about who gets infections (BUG-002). The graph is rebuilt from a CSV by an importer that validates the data and replaces only its own snapshot. See FLOW.md. Every merge that changes shipped files becomes its own release, tagged only after every check passes, and the owner's local stack updates itself from those releases with a backup and automatic rollback.

**Key decisions and why X over Y.**
- Graph and templates over a generative model: every answer is an inspectable query result, at the cost of understanding fewer phrasings.
- Abstaining over the old similarity fallback: the fallback returned other patients' answers to unrelated questions.
- Quarantining bad data over repairing it: no invented medical terms.
- No authentication over a shared token or accounts: the API is read-only over public data and only listens on this machine, so a token protected nothing and added friction; nginx rate-limits floods instead.
- Native path filters over a CI orchestrator: nothing runs for docs-only changes.
- Guided conversation without a language model over LLM-written answers: every answer stays a graph fact, and the API stays stateless because the page sends the topic back (D-015).
- A language model that only routes over one that answers (D-026, D-027): it chooses among names the rules found, so every answer is still a graph fact; it reads paraphrases and negation far better, and any failure falls back to the rules. The owner integrated it before it met the pre-registered bar, accepting that questions go to Ollama's cloud.
- Suggestions from a table the importer writes over a database lookup per request: no extra query or timeout on the answer path (D-016).
- Sourced aliases and confirmed spelling suggestions over silent fuzzy matching: a near-miss can be a different disease (D-017).
- One release per merge, tagged only after every gate, over manual tags or tag-then-test: a failed release uses up no version, and releases stay in merge order (D-019, D-020).
- A Docker Hub copy of each release by digest, in its own run, over pushing from the release itself: users can pull from Docker Hub, and a Docker Hub outage never blocks a release (D-030).
- A free VM for the API and page, AuraDB Free for the graph and a Cloudflare Tunnel over opening ports or paid hosting: HTTPS with no inbound port, and the VM closes public access while it rebuilds the graph (D-032).
- A scheduled pull-based updater over a self-hosted runner: no inbound access, and no way for other people's pull requests to run code on this machine (D-021).

**Data structures and why.** A Neo4j graph with unique-name constraints, because every lookup is "facts about this named disease or symptom". An in-memory Aho-Corasick automaton, because it finds every known name in one pass over the question. See DATA.md.

**How a malicious actor could abuse it.** Anyone who can reach it can only send rate-limited, 500-character GET questions, which become query parameters, never query text. The follow-up topic and clarification choices are checked against the dictionary and never logged. Answers render as plain text, and questions and tokens never reach a log. With the language model on, questions and candidate names go to Ollama's cloud; the model can only choose among locally found names and allowed question types, and every API response is marked `no-store`. The hosted site (D-032) is public without login: Cloudflare carries it, nginx limits each real visitor and caps API requests in flight, and the model may read questions there through Ollama's cloud, at most 6 calls a minute for everyone together (D-033). The real gaps are one API worker for every visitor, auto-merging and auto-releasing without human review, and a dataset whose facts are not clinically reviewed. Whoever can publish a release can ship images to the owner's machine; the updater accepts only digest-pinned images from this repository and a `compose.yaml` identical to the one the owner enrolled. See THREAT.md.

**Where it fails and how we notice.** If Neo4j is down or slow, users get a 503 message and the error is logged. A stale or empty graph makes every answer an abstention; `GET /health` and the Docker healthcheck now report an empty, resized or differently sourced graph, and the CI evaluation catches the rest. The first limit under load is the single gunicorn worker. There is no alerting. A failed release stops the release chain until fixed, and a failed local update restores the previous release and its graph backup. See FAILURE.md.

**What I would change with more time.** Replace the unverified CSV with sourced data (MedlinePlus + Disease Ontology, behind rights and evaluation gates). Move the question out of the URL into a POST body. Publish the graph and dictionary as one unit (D35). Make the language model meet its pre-registered bar on a fresh set (reliability and latency missed in Round 2), and widen the reworded answers once the owner has reviewed the pilot.
